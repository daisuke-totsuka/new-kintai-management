# テストデータ管理

## 目的

テストデータの命名、作成、Cleanup、Mock、実DB、Supabase、本番DB禁止、テストユーザー、支店900番台利用を標準化する。

## 基本方針

- テストデータは再実行可能で、他のテストと衝突しないことを前提に作る。
- 実DBを使う場合は、作成データを識別できる命名とCleanupを必須にする。
- Mockで検証できるものはMockを優先し、DB制約や実連携が必要なものだけ実DBを使う。
- 本番DBをテスト用途に使用しない。

## 命名規則

| 対象 | 規則 | 例 |
|---|---|---|
| テストユーザー | `test.<role>.<purpose>@example.com` | `test.admin@example.com` |
| 一時メール | `integration_test_<timestamp>@example.com` | `integration_test_20260804120818@example.com` |
| 社員ID | 900番台またはテスト専用範囲を使う | `9000000001` |
| 支店コード | 900〜999を使う | `900`, `901` |
| 権限ID | テスト用途が分かる接頭辞を付ける | `TEST_MANAGER` |
| 備考/名称 | `TEST_` または `テスト_` を含める | `TEST_BRANCH_900` |

## Cleanup

- 実DBテストで作成したデータはテスト終了時に削除または無効化する。
- Cleanupは作成順の逆順で行う。
- 外部キー相当がある場合は子テーブルから削除する。
- Cleanup失敗時は対象テーブル、キー、残データのリスクを記録する。
- テストが途中失敗してもCleanupが実行されるようにする。

## 実DB利用

実DBテストは次の場合に限る。

- DB制約、桁数、境界値を実DBで確認する必要がある。
- Supabase連携、認証、RLS相当の挙動を確認する必要がある。
- RepositoryやAPIのMockでは検証できない差異がある。

実DB利用時は次を必須とする。

- 接続先がテストDBであることを確認する。
- 対象データのキー範囲を明示する。
- Cleanup手順を明示する。
- 本番データと衝突しない採番にする。

## Mock利用

- UI表示、入力状態、エラー表示、API失敗表示はMockを優先する。
- Backend Serviceの単体テストではRepositoryや外部サービスをMockしてよい。
- Mockは正常系だけでなく異常系、空配列、null、タイムアウト相当を用意する。
- Mockで通るだけではDB制約確認済みと扱わない。

## Supabase利用

- Supabaseはテスト用プロジェクトまたはテスト用schemaを使用する。
- 接続情報は環境変数で管理し、リポジトリに秘密情報を含めない。
- テスト実行前に対象テーブル、RLS相当、初期データを確認する。
- 実DBテストは環境がない場合SKIPしてよいが、SKIP理由を明確にする。

## 本番DB禁止

- 本番DB、利用者データを含むDB、復元困難な共有DBでのテストは禁止する。
- 本番URL、本番キー、本番schemaが検出された場合はテストを停止する。
- 誤接続防止のため、テストコードでは環境名またはURLを検査する。

## テストユーザー

- ロール別に標準テストユーザーを用意する。
- ADMIN、USER、LEADER、ACCOUNTING、ADMIN_ACCOUNTINGなど、権限確認に必要なロールを保持する。
- パスワードやトークンは環境変数またはテスト専用シークレットで管理する。
- テストユーザーは本番ユーザーと同じメールドメインを使わない。

## 支店900番台利用

- 支店実DBテストでは支店コード900〜999をテスト専用範囲とする。
- 900番台の空きがない場合は、テストをSKIPし、理由を結果に残す。
- 900番台支店は作成者、更新者、作成日時でテスト由来と判別できるようにする。
- 支店責任者や関連ユーザーもテスト専用IDを使う。

## データ分類

| 分類 | 用途 | 管理方法 |
|---|---|---|
| 固定マスタ | ロール、メニュー、勤務区分など | migrationまたはseedで管理 |
| テスト固定データ | 権限別ユーザー、標準支店など | テスト環境専用seedで管理 |
| 一時データ | 登録、更新、削除確認 | テスト内で作成しCleanup |
| Mockデータ | UI、Service単体、異常応答 | テストファイル内またはfixtureで管理 |
