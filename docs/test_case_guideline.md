# テストケース記述ガイドライン

## 目的

テストケースの粒度、命名、期待結果、metadata、Excel出力の記述ルールを統一する。

## 基本ルール

- 1テストケースは1つの観点に絞る。
- テスト名は何を検証するかが分かる文章にする。
- Frontendの `it(...)` は日本語を原則とする。Next API Proxyなど技術分類でもExcel表示名は日本語にする。
- Backendの pytest関数名は英語のままでよいが、metadataの `screenName` と `expected` は日本語を原則とする。
- 正常系だけでなく、異常系、境界値、桁数、入力形式、権限、認証、DB、排他を含める。
- テストを追加したらmetadataを同時に追加する。

## 必須記述項目

| 項目 | 記述ルール |
|---|---|
| testId | 画面またはAPI単位で一意にする |
| type | Frontend、Backend、API、DB、E2Eなどを明示する |
| screenName | 正式日本語画面名または日本語分類名を書く |
| testName | 実テスト名と完全一致させる |
| input | 入力値、前提状態、API payload、DB状態を書く |
| expected | 利用者またはAPI利用者から見た期待結果を書く |
| actual | 正常時は期待結果と同等の確認内容を書く |
| nodeid | Backendでpytest結果と紐づける場合に書く |

## テスト観点

### 正常系

- 一覧表示、検索、登録、更新、削除、保存、提出、遷移を確認する。
- APIでは200/201などの成功ステータス、レスポンス形式、DB反映を確認する。
- 画面では表示文言、ボタン状態、入力反映、成功メッセージを確認する。

### 異常系

- 必須未入力、不正値、存在しないID、権限不足、認証切れ、Backendエラーを確認する。
- DB更新が発生しないことを確認する。
- Frontendでは技術詳細を利用者に出しすぎないことを確認する。

### 境界値

- 最小値、最大値、最小値-1、最大値+1を確認する。
- 日付、月、日、時間、分、数値範囲、状態遷移を対象にする。
- DB制約と業務制約の両方を確認する。

### 桁数

- DB定義の最大桁数ちょうど、最大桁数+1を確認する。
- ID、名称、メール、備考、コード、数値項目を対象にする。
- 受理と拒否の期待結果を明確に分ける。

### 入力形式

- メール、時刻、年月、日付、数値、UUID、コード値の形式を確認する。
- Frontendで入力制御していてもBackendで再検証する。
- 空白、全角、記号、前後スペースの扱いを明示する。

### 権限

- role_id別に参照、登録、更新、削除、メニュー表示を確認する。
- 許可ロールと拒否ロールを両方確認する。
- Frontendの非表示だけでなくBackendの403相当を確認する。

### 認証

- 未ログイン、期限切れ、Cookieなし、不正トークンを確認する。
- `/auth/me`、ログイン、Next API ProxyのCookie転送を確認する。
- 認証失敗時はDB更新しないことを確認する。

### API

- HTTPメソッド、path、query、payload、headers、Cookieを明示する。
- 成功、400、401、403、404、409、500相当を必要に応じて確認する。
- エラーレスポンスの `code`, `field`, `message`, `detail` の扱いを確認する。

### DB

- INSERT、UPDATE、DELETE、論理削除、未更新を確認する。
- created_by、updated_by、created_at、updated_atなど監査列を確認する。
- DB制約、ユニーク制約、外部キー相当、桁数、境界値を確認する。

### 排他

- `updated_at` または `baseUpdatedAt` の不一致を確認する。
- 409発生時の最新データ、差分セル、再保存可否を確認する。
- E2Eでは複数セッションまたは同等の状態を作って確認する。

## E001〜E020

- 勤務実績の業務エラーはE001〜E020単位でテスト観点を作る。
- `docs/attendance_error_codes.md` を正とし、未確定のE012は残課題として扱う。
- Frontendは表示、セル強調、エラー一覧、スクロールを確認する。
- Backendは検出条件、field、message、保存可否、提出可否を確認する。
- エラーコード追加または仕様変更時はmetadataとExcel期待結果を更新する。

## 期待結果の書き方

- 「表示される」「保存される」だけでなく、何がどの値で確認できるかを書く。
- 異常系は「拒否される」「DB更新されない」「利用者向けメッセージが出る」を明記する。
- 境界値は「最大値ちょうどはOK」「最大値+1はNG」のように受理条件を明確にする。
- APIはステータス、レスポンス、DB副作用をセットで書く。

## Excel出力

- metadataの `screenName` ごとにExcelファイルが分割される。
- `screenName` は日本語名で統一する。
- `testName` が実行結果と一致しない場合、Excel生成失敗または未出力になる。
- Excel出力後、ファイル名、画面名列、判定、期待結果、実際結果を確認する。
