# テスト方針

## 目的

本プロジェクトのテスト方針、品質ゲート、実DB利用、Excelレポート運用を標準化する。新規実装、不具合修正、回帰確認では本方針を必ず参照する。

## 基本方針

- 実装とテストは同一作業単位で作成する。
- 業務ルールはBackendのテストを正とし、Frontendは表示、入力補助、操作導線を検証する。
- 入力エラー、境界値、桁数、権限、認証、排他制御は正常系と同じ重要度で扱う。
- テスト結果はmetadataとExcelレポートにより追跡可能にする。
- 本番DBをテストに使用しない。

## テストレベル

| レベル | 対象 | 目的 | 必須条件 |
|---|---|---|---|
| 単体 | 関数、Service、Repository、UI部品 | 個別ロジックを高速に検証する | 正常系、異常系、境界値を含める |
| API | Backend API、Next API Proxy | HTTPステータス、payload、Cookie、認証、DB反映を検証する | metadataとExcel出力対象にする |
| 画面 | React画面、フォーム、一覧、ナビゲーション | 表示、入力、エラー、操作状態を検証する | screenNameを正式日本語名にする |
| 結合 | API、Repository、DB、認証の連携 | モジュール間契約を検証する | 外部依存を明示する |
| 実DB | Supabaseなどテスト用DB | DB制約、実データ連携、RLS相当の差異を確認する | テストDBのみ、Cleanup必須 |
| E2E | 代表的な業務フロー | 利用者視点の一連操作を検証する | 最小限の安定シナリオに絞る |
| 回帰 | 既存仕様、不具合再発 | 変更影響を検証する | 修正箇所と周辺仕様を含める |
| Build | Frontend/Backendのビルド、型、起動確認 | 配布可能性を検証する | 対象範囲のBuild成功を品質ゲートにする |
| Excel | テスト結果Excel | 結果証跡とレビュー資料を作る | metadataと一致し、日本語名で出力する |

## 品質ゲート

変更完了の標準条件は次の通り。

- 対象テストがすべて成功している。
- 新規または変更したテストにmetadataが存在する。
- `testName` とテスト実行結果のタイトルが一致している。
- Excelレポートが生成できる。
- `screenName` が正式な日本語画面名または日本語分類名である。
- Frontend変更では必要に応じてBuildが成功している。
- API/DB変更では必要に応じてDB反映またはRepository層の確認ができている。
- 実DBテストを行った場合、Cleanupが完了している。

## 必須テスト項目

### 入力エラー正常動作チェック

- 必須未入力、不正形式、範囲外、存在しない参照値を検証する。
- エラー時に保存、更新、削除などの副作用が発生しないことを確認する。
- Frontendでは利用者向けメッセージ、赤色エラー領域、対象セル強調、スクロール導線を確認する。
- BackendではHTTPステータス、エラーコード、field、message、DB未更新を確認する。

### DB入力桁数限界値チェック

- DB定義、業務仕様、APIバリデーションの最大桁数を確認する。
- 最大桁数ちょうどは受理、最大桁数+1は拒否を原則とする。
- 文字列、ID、メール、名称、備考、数値項目を対象にする。

### DB入力境界値チェック

- 日付、月、日、時間、分、数値、状態値、コード値の最小値、最大値、範囲外を確認する。
- 1日/31日、1月/12月、0分/上限分など、仕様上の境界を明示する。
- DB制約とアプリ側バリデーションのどちらで防ぐかをmetadataに記録する。

## metadata運用

- Frontend metadataは `frontend/tests/metadata/*.metadata.json` に配置する。
- Backend metadataは `backend/tests/metadata/*.metadata.json` に配置する。
- 必須項目は `testId`, `type`, `screenName`, `testName`, `input`, `expected`, `actual` とする。
- Backendでは必要に応じて `nodeid` を付与し、pytest結果と確実に紐づける。
- `screenName` はExcelファイル名になるため、英語名、コンポーネント名、ルート名をそのまま使わない。
- `testName` はテスト実装の `it(...)` または pytest関数名と一致させる。

## 実DB利用ルール

- 実DBはテスト専用SupabaseまたはローカルDBのみ使用する。
- 本番DB、共有検証DB、利用者データを含むDBは禁止する。
- 実DBテストは、対象データ、作成者、削除方法、再実行性を明示する。
- 支店テストは900番台の支店コードを利用し、既存業務データと衝突させない。
- テスト終了後は作成データをCleanupする。

## CI適用方針

- 通常CIでは単体、API、画面、metadata整合、Excel生成、Buildを段階的に実行する。
- 実DBとE2Eは環境変数とテストDBが用意された場合のみ実行する。
- PRでは軽量テストを必須、夜間または手動で実DB/E2Eを実行する。
- Excel生成失敗、metadata不一致、英語screenName混入はCI失敗扱いにする。

## 新規画面の標準ルール

新規画面を追加する場合は、実装と同時に次を行う。

1. 画面テストを作成する。
2. metadataを追加する。
3. `screenName` を正式日本語画面名にする。
4. Excel生成を確認する。
5. Build成功を確認する。
6. DB参照または更新がある場合は、必要に応じてAPI/実DB確認を行う。

## 新規APIの標準ルール

新規APIを追加する場合は、実装と同時に次を行う。

1. APIテストを作成する。
2. DB更新、DB未更新、境界値、権限、認証を確認する。
3. metadataを追加する。
4. Excel生成を確認する。
5. 実DB確認が必要な場合はテストDBとCleanup手順を明示する。

## 不具合修正ルール

不具合修正では次の順序を標準とする。

1. 再現テストを追加する。
2. 修正する。
3. 回帰テストを実行する。
4. Excelレポートを更新する。

再現テストを作れない場合は、理由、代替確認、残リスクを明記する。

## 残課題

| 課題 | 現状 | 標準対応 |
|---|---|---|
| E012 | VBA上の有効判定条件が未確定 | 仕様確定後、Backend Service、Frontend表示、metadata、Excelを更新する |
| Backend API残り4件 | APIテスト未整備の残件がある | API別に正常系、異常系、DB確認、metadataを追加する |
| 支店実DBテスト | 900番台支店コード不足時にSKIPされる | テスト用支店900番台データの準備とCleanupを標準化する |
| 排他制御E2E | 単体/API中心でE2Eが不足 | 複数セッション更新、409、再取得、再保存のE2Eを追加する |
